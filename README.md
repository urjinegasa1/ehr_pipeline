# Healthcare/EHR Data Pipeline — Readmission Risk Prediction

End-to-end data engineering pipeline for Assessment 2, Topic 4
(Healthcare/EHR Data Pipeline): ingestion → storage → cleaning →
feature engineering → Great Expectations validation → PySpark
processing → Airflow orchestration → DVC versioning → ML-ready dataset.

## ⚠️ Before you submit: swap in the real dataset

This repo ships with a **synthetic dataset** (`src/generate_raw_sources.py`)
that mirrors the exact column schema, value domains, and realistic messiness
of the real [UCI Diabetes 130-US Hospitals dataset](https://archive.ics.uci.edu/dataset/296/diabetes+130-us+hospitals+for+years+1999-2008)
(20,000 encounters here; the real dataset has ~101,766). It was generated
this way because this build environment has no network access to
archive.ics.uci.edu or kaggle.com. **Swap it in before you submit:**

1. Download `diabetic_data.csv` from the UCI link above (or the Kaggle
   "EHR Cancer Diagnosis" dataset, which the assignment also allows for
   this topic).
2. Save it as `data/raw/ehr_encounters.csv` with matching column names
   (see `docs/data_dictionary.md` for the exact schema), or adjust the
   column mapping at the top of `src/transform.py` if the real file's
   column names differ slightly.
3. Keep `src/generate_raw_sources.py`'s lab-API simulation as your second
   source (the assignment explicitly allows a "simulated healthcare API"
   for this topic), or replace it with a second real dataset if required.
4. Re-run the pipeline (Step 3 below). Cleaning, features, GX, Spark,
   Airflow, and DVC all key off column names, not row counts, so nothing
   else needs to change.

## 0. Prerequisites

- Python 3.10+
- Java 11+ (required by PySpark)
- `pip install -r requirements.txt`

## 1. Project layout


## 2. Setup

```bash
cd ehr_pipeline
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## 3. Run the full pipeline locally (fastest way to test / for your demo recording)

```bash
python src/pipeline_main.py
```

This runs, in order: ingestion → storage → cleaning/transform → feature
engineering → Great Expectations validation → PySpark processing. Outputs:

- `data/processed/ehr_ml_ready.parquet` and `.csv` — final ML-ready dataset
- SQLite table `processed_ehr_ml_ready` in `data/warehouse.db`
- `docs/data_quality_report.json` — GX validation summary
- `data/processed/spark_aggregates/` — Spark aggregation outputs

## 4. Run individual phases

```bash
python src/generate_raw_sources.py   # regenerate raw sources
python src/storage.py                # (re)load raw -> SQLite + Parquet
python src/transform.py              # clean + join
python src/features.py               # engineer features + build ML-ready output
python src/quality.py                # run Great Expectations suite
python src/spark_processing.py       # PySpark aggregations
```

## 5. Orchestrate with Airflow

```bash
export AIRFLOW_HOME=~/airflow
pip install apache-airflow
cp dags/ehr_pipeline_dag.py $AIRFLOW_HOME/dags/
airflow db init
airflow users create --username admin --password admin --firstname A --lastname B --role Admin --email a@b.com
airflow webserver --port 8080 &
airflow scheduler &
# then trigger from the UI, or:
airflow dags trigger ehr_healthcare_pipeline
```

The DAG (`ehr_healthcare_pipeline`) runs the same 7 tasks in the same order
as `pipeline_main.py`, scheduled nightly at 02:00, with retries and a
failure-alert hook on every task, and halts before the Spark step if data
quality validation fails.

## 6. Data versioning with DVC

```bash
dvc init                     # already done in this repo
dvc remote add -d localremote /path/to/your/remote   # swap for S3/GCS/Azure in prod
dvc add data/raw/ehr_encounters.csv data/raw/ehr_lab_api_extract.json
dvc add data/processed/ehr_ml_ready.parquet data/processed/ehr_ml_ready.csv
dvc push                     # push data to the remote
git add data/**/*.dvc .dvc/config
git commit -m "Track v1 of raw + processed EHR datasets"
```

To reproduce a prior version: `git checkout <commit> -- data/raw/*.dvc && dvc pull`.

## 7. Data quality

18 Great Expectations checks covering primary-key uniqueness, completeness,
clinical range plausibility (BMI, blood pressure, creatinine, HbA1c), and
categorical domain validity. See `docs/data_quality_report.json` for the
latest run and `src/quality.py` for the full suite definition.

## 8. Notes on privacy

`patient_id` is used only as a join key between the two sources and is
dropped before the ML-ready dataset is written (see
`docs/data_dictionary.md`, "Columns dropped"). DVC-tracked datasets should
be stored in an access-controlled remote in production, consistent with
the assignment's "anonymized" DVC-versioning guidance for this topic.
